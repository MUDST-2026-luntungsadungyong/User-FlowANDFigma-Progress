🛡️ 1. Platform Admin & Seller Approval Architecture

สิทธิ์และการจัดการ Admin:

  • ฟิลด์ users.role รองรับ 'USER' และ 'ADMIN' (Platform Admin)
  • Admin มีอำนาจแต่งตั้ง User อื่นให้เป็น Admin ได้ โดยทุกการกระทำจะถูกบันทึกลง audit_logs
  • Admin สามารถจัดการการ์ด Global (เพิ่ม/แก้ไข/ระงับ is_active) ในระบบแคตตาล็อกกลาง

Seller Verification Gate (การอนุมัติผู้ขาย):

1 Buyer ยื่นขอ: กรอกชื่อร้าน, เลขบัตร/เอกสารยืนยันตัวตน, และเลขบัญชีธนาคารรับเงิน → สถานะเป็น PENDING
2 Admin ตรวจสอบ: อนุมัติ (APPROVED พร้อมบันทึก approved_by) หรือ ปฏิเสธ (REJECTED พร้อมระบุ rejection_reason)

🌐 2. Global Cards vs 🏷️ Local Cards Marketplace Model

หัวใจสำคัญ: การ์ด Global ทั้งระบบ "ไม่จำเป็นต้องมีเจ้าของ" แต่การ์ด Local ทุกใบที่ขายในระบบ "ต้องมี Seller เป็นเจ้าของเสมอ 100%"

มิติเปรียบเทียบ 🌐 Global Cards (global_cards) 🏷️ Local Cards (local_cards)
ความเป็นเจ้าของ ไม่มีเจ้าของ (Ownerless) เป็นสารบรรณการ์ดกลางของระบบ ต้องมีเจ้าของเสมอ 100% (seller_id)
ผู้จัดการข้อมูล Platform Admin (หรือ Import จาก Pokémon TCG API) Seller แต่ละร้านค้า เป็นผู้ตั้งราคาและจัดการสต็อกของตน
รูปภาพ & สภาพ รูป Official Artwork มาตรฐานจากการ์ดชุดนั้น รูปถ่ายสภาพจริง (custom_image_url) ที่ Seller ถ่ายจากของจริง พร้อมระบุสภาพ (NM, LP, etc.)
การแสดงผลในเว็บ หน้า Search/Catalog กลาง: เมื่อ Buyer คลิกดูการ์ด Global 1 ใบ จะมี "List of Available Sellers" แสดงร้านค้าทั้งหมดที่ขายการ์ดนี้ หน้ารายการสินค้าของร้านค้า: ผู้ซื้อสามารถเปรียบเทียบราคา, สภาพ, รูปถ่ายจริง, และกดเลือกซื้อจากร้านที่ต้องการได้โดยตรง

📊 3. Platform Admin Dashboard & Transaction Integrity

Admin Dashboard High-Speed Metrics:

  • จำนวนการ์ดในระบบ: COUNT(*) FROM global_cards WHERE is_active = true
  • จำนวน User แยก Buyer / Seller:
    • Buyer: COUNT(*) WHERE role = 'USER' AND seller_status != 'APPROVED'
    • Seller: COUNT(*) WHERE seller_status = 'APPROVED'
  • ยอดเงินทั้งหมดในระบบ (GMV): SUM(total_amount) FROM orders WHERE status = 'PAID'
  • รายได้ค่าธรรมเนียม Platform: SUM(platform_fee) FROM orders WHERE status = 'PAID'

Data Integrity & Safety Guarantees:

  • Stock Over-selling Prevention: มี Database Check Constraints บังคับ on_hand >= 0 และ reserved <= on_hand เสมอ
  • Double-Payment Prevention: กำกับ UNIQUE (buyer_id, idempotency_key) ที่ตาราง orders
  • Snapshot Pattern: ตาราง order_items คัดลอกชื่อสินค้า, ชื่อร้าน, และราคา ณ วันที่ซื้อแบบ Immutable เพื่อป้องกันข้อมูลเพี้ยนหากผู้ขายแก้โปรไฟล์
